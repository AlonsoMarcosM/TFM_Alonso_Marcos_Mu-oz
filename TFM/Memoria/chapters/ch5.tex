\section{Fuente técnica reproducible: PostgreSQL en tres capas}\label{sec:implementacion-postgres}

La fuente técnica es un PostgreSQL desplegado en el mismo clúster Kubernetes que \ac{OM}, inicializado a partir de \texttt{sql/opendata\_demo\_init.sql}~\cite{postgresqlDocs}. El \ac{SQL} crea tres esquemas alineados con el patrón \emph{medallion} (bronze/silver/gold), de modo que el caso de uso de validación dispone de datos sintéticos verosímiles sin depender de descargas externas. Únicamente el esquema \texttt{gold} se considera publicable: las capas \texttt{bronze} y \texttt{silver} se ingieren en el catálogo técnico para mantener la cadena de transformaciones visible, pero no se exportan como datasets \ac{DCATAPES} por las razones de conformidad semántica, alineamiento con \ac{DMBOK} y separación entre catálogo técnico y catálogo de publicación que se argumentan en la sección~\ref{sec:decision-gold-only}.

El listado~\ref{code:postgres-gold} muestra la creación de la tabla \texttt{gold.agenda\_cultural\_publica}, que después se convierte en uno de los datasets del catálogo \ac{DCATAPES}. La estructura es suficientemente expresiva (claves temporales, dimensiones territoriales, métricas) para que el catálogo exportado contenga campos significativos al validar con \ac{SHACL}.

\begin{lstlisting}[language=SQL, caption={Fragmento de \texttt{sql/opendata\_demo\_init.sql}: tabla publicable de la capa gold.}, label=code:postgres-gold, captionpos=b]
CREATE SCHEMA IF NOT EXISTS gold;

CREATE TABLE IF NOT EXISTS gold.agenda_cultural_publica (
    evento_id        BIGINT      PRIMARY KEY,
    fecha            DATE        NOT NULL,
    municipio        TEXT        NOT NULL,
    categoria        TEXT        NOT NULL,
    titulo           TEXT        NOT NULL,
    asistencia_est   INTEGER     CHECK (asistencia_est >= 0),
    actualizado_en   TIMESTAMPTZ DEFAULT now()
);
\end{lstlisting}

\section{Despliegue reproducible en Kubernetes}\label{sec:implementacion-k8s}

El despliegue local utiliza Kind como motor de clúster Kubernetes encima de Docker~\cite{dockerOverview, kindDocs, kubernetesConcepts}. \ac{OM} y sus dependencias (MySQL y OpenSearch) se instalan mediante Helm~\cite{helmDocs} usando los \emph{values} canónicos del repositorio. La figura~\ref{fig:docker-containers} muestra los contenedores Docker reales del entorno y la figura~\ref{fig:pods-kubernetes} los \emph{pods} resultantes en el clúster.

\begin{lstlisting}[language=yaml, caption={Fragmento de \texttt{k8s/openmetadata.values.yaml}: configuración mínima del release Helm.}, label=code:k8s-values, captionpos=b]
openmetadata:
  config:
    elasticsearch:
      host: opensearch
      port: 9200
    database:
      host: mysql
      port: 3306
      driverClass: com.mysql.cj.jdbc.Driver
\end{lstlisting}

El script \texttt{scripts/infra/launch\_infra.ps1} encadena la creación del clúster, la instalación de los charts y los \texttt{port-forward} necesarios para exponer la \ac{UI} de \ac{OM} en \texttt{localhost:8585} y el PostgreSQL de referencia en \texttt{localhost:5432}. La idempotencia se garantiza mediante \texttt{helm upgrade --install} y comprobaciones con \texttt{kubectl get} previas a cada paso destructivo. Los \emph{values} Helm canónicos y notas operativas adicionales se describen en el Anexo~\ref{ap:infraestructura}.

\section{Doble ingesta técnica}\label{sec:implementacion-ingesta}

La ingesta se ejecuta dos veces sobre la misma base PostgreSQL, registrando dos \texttt{DatabaseService} diferenciados en \ac{OM}: \fqn{postgres_demo_service} y \fqn{postgres_validation_service}. Este patrón demuestra que la lógica de gobierno opera sobre \acp{FQN}, no sobre nombres cortos de tabla; dos tablas con idéntico nombre funcional procedentes de servicios diferentes generan datasets independientes en el catálogo final.

La ingesta se invoca desde \fqn{scripts/infra/ingest_postgres_double.ps1}, que llama a los \emph{workflows} de ingesta de \ac{OM}~\cite{openmetadataDocs} con dos configuraciones diferenciadas. El resultado es visible en la \ac{UI} de \ac{OM} (figura~\ref{fig:om-services}): cuatro tablas publicables (dos por servicio), cada una con su \ac{FQN} único.

\subsection{Configuración inmutable y entrypoint}

El módulo \fqn{workflow_service.py} define una \texttt{dataclass} inmutable (\texttt{frozen=True})~\cite{pythonDataclasses} que fija todos los parámetros del workflow antes de su ejecución, evitando estados mutables compartidos entre llamadas. El listado~\ref{code:workflow-service-impl} amplía el listado~\ref{code:workflow-service} con la secuencia operativa real.

\begin{lstlisting}[language=Python, caption={Esqueleto de \texttt{run\_workflow} en \texttt{workflow\_service.py}.}, label=code:workflow-service-impl, captionpos=b]
def run_workflow(config: WorkflowRunConfig) -> dict[str, Any]:
    defaults = load_defaults(config.defaults_path)
    rules    = load_rules(config.rules_path)
    api      = OpenMetadataApi(base_url=config.base_url, jwt_token=config.token)
    tables   = discover_tables(api=api, limit=config.limit)

    # 1) Refrescar la hoja desde activos descubiertos sin perder curación previa
    if config.refresh_sheet:
        existing = load_governance_sheet(config.sheet_path) if Path(config.sheet_path).exists() else []
        generate_governance_sheet(tables, defaults, config.sheet_path, existing_rows=existing,
                                  tags_by_prefix=rules.table_tags_by_prefix)

    # 2) Sincronizar gobierno hacia OpenMetadata (idempotente)
    plan = run_governance_sync(api=api, sheet_path=config.sheet_path,
                               defaults=defaults, rules=rules, dry_run=config.dry_run)

    # 3) Exportar el catálogo DCAT-AP-ES y 4) validar con SHACL
    if not config.skip_export:
        export_catalog(api=api, defaults=defaults, output=config.export_output)
    if not config.skip_validate:
        export_and_validate_catalog(profile_case=config.profile_case,
                                    report_output=config.report_output,
                                    allow_warnings=config.allow_warnings)
    return {"plan": plan, "sheet_refreshed": config.refresh_sheet}
\end{lstlisting}

\subsection{Sincronización idempotente de gobierno}

\texttt{governance\_service.py} mapea cada fila de la hoja \ac{CSV} a operaciones \texttt{PATCH} o \texttt{POST} sobre la entidad correspondiente en \ac{OM} usando su \ac{FQN}. La idempotencia se materializa por dos vías: las propiedades gestionadas (\texttt{MANAGED\_DCAT\_CUSTOM\_PROPERTIES}) solo se reescriben si cambian, y las etiquetas \texttt{dcat\_theme.*} se aplican como conjuntos, nunca como acumulación lineal. La consecuencia operativa es que ejecutar el workflow dos veces consecutivas produce cero cambios en la segunda ejecución, lo que constituye una de las métricas de validación documentadas en el capítulo~\ref{cap:validacion}.

El resultado del gobierno es directamente observable en \ac{OM}: tras el workflow, cada tabla \texttt{gold} publicable conserva sus propiedades personalizadas DCAT (\fqn{dcat_publisher_name}, \fqn{dcat_hvd_category}, \fqn{dcat_access_url}) y sus etiquetas \fqn{dcat_theme.*}, que son la materia prima que el exportador transforma en el grafo \ac{DCATAPES} (figura~\ref{fig:om-tabla-propiedades}).

\figuraMemoria{fig_om_tabla_propiedades.png}{Propiedades personalizadas DCAT y etiquetas \texttt{dcat\_theme.*} aplicadas a una tabla \texttt{gold} en OpenMetadata tras ejecutar el workflow. Elaboración propia.}{fig:om-tabla-propiedades}

\subsection{Exportador \texorpdfstring{\ac{DCATAPES}}{DCAT-AP-ES}}

\texttt{dcat\_export.py} compone el grafo conceptual a partir de las clases activas: \texttt{dcat:Catalog}, \texttt{dcat:Dataset}, \texttt{dcat:Distribution}, \texttt{dcat:DataService} y \texttt{foaf:Agent}. La construcción se hace en Python puro mediante diccionarios anidados que respetan el contexto \ac{JSONLD}; cuando es necesario manipular el grafo (normalización, deduplicación), se delega en RDFLib~\cite{rdflib}.

El listado~\ref{code:dcat-export-context} muestra el contexto \ac{JSONLD} canónico utilizado: prefijos estables, idioma por defecto en español y enlace a vocabularios temáticos de NTI-RISP~\cite{datosGobNtiRisp}.

\subsection{Validación SHACL del catálogo exportado}

\fqn{shacl_validation.py} aplica el bundle vendorizado en \fqn{tfm_ingestor/resources/shacl/} con pySHACL~\cite{pyshacl}. El bundle está congelado en el commit \texttt{f2c8a888} de \fqn{datosgobes/DCAT-AP-ES}~\cite{datosGobValidacionDcatApEs2025} para evitar dependencias de red y garantizar reproducibilidad entre ejecuciones. El validador devuelve un informe Turtle estructurado por \texttt{sh:focusNode}, \texttt{sh:resultPath}, \texttt{sh:severity} y \texttt{sh:resultMessage}; el módulo lo postprocesa para filtrar \texttt{sh:Warning} cuando se pasa \texttt{-{}-allow-warnings}.

\section{Hoja funcional de gobierno y defaults globales}\label{sec:implementacion-hoja}

La curación funcional se concentra en \texttt{tfm\_ingestor/config/gold\_governance.csv}, cuya estructura columnar se describe en la tabla~\ref{tab:hoja-gobierno-columnas} y se detalla con criterios de validación en el Anexo~\ref{ap:ingesta-gobierno}. El uso de \ac{CSV} con separador \texttt{;} no es accidental: facilita la edición en hojas de cálculo locales sin Excel y, sobre todo, hace que el diff en Git sea legible para revisión editorial. Los defaults globales viven en \texttt{governance\_defaults.yaml}, que centraliza publicador, homepage, idioma, licencia, contacto y la legislación \ac{HVD} aplicable (Reglamento de Ejecución (UE) 2023/138~\cite{euHvdRegulation}).

La figura~\ref{fig:web-pantalla-gobierno} muestra la pantalla \emph{Gobierno} de la consola web, que actúa sobre la misma hoja \ac{CSV} y aplica las mismas reglas de validación que el \ac{CLI}. El uso real de esta pantalla durante una sesión completa se narra en la sección~\ref{sec:demo-gobierno} del Anexo~\ref{ap:demo-operativa}.

\section{Consola web operativa Next.js}\label{sec:implementacion-web}

La consola web se construye con Next.js~\cite{nextjsDocs}, React~\cite{reactDocs} y TypeScript~\cite{typescriptHandbook}, organizada en rutas que mapean uno-a-uno con las etapas del workflow: \emph{Infraestructura}, \emph{Ingesta}, \emph{Gobierno}, \emph{Workflow}, \emph{DCAT}, \emph{Estado vivo}, \emph{Validación}, \emph{SHACL}, \emph{Artefactos}, \emph{Ejecuciones}. La arquitectura interna respeta la regla de núcleo único: la \ac{UI} nunca habla directamente con \ac{OM} ni reimplementa reglas, sino que invoca una lista cerrada de operaciones de servidor (\texttt{operations.ts}) que a su vez ejecutan el \ac{CLI} o los scripts PowerShell. La descripción operativa pantalla a pantalla, incluyendo los artefactos producidos en cada paso, se desarrolla en el Anexo~\ref{ap:demo-operativa}; los comandos equivalentes desde \ac{CLI} y \texttt{pnpm} están recogidos en el Anexo~\ref{ap:validacion-web}.

\section{Resumen de implementación}

La implementación cumple las tres reglas duras declaradas en el capítulo~\ref{cap:arquitectura}: una única lógica de negocio en Python, idempotencia comprobable y separación estricta entre datos técnicos, curación funcional y derivaciones automáticas.
